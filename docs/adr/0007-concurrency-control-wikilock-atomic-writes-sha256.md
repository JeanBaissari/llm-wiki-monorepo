# ADR 007: Concurrency Control — WikiLock + Atomic Writes + SHA256 Conflict Detection

- **Status:** accepted
- **Date:** 2026-07-04
- **Context:** Multiple agents or processes may write to the same wiki simultaneously. Without concurrency control, concurrent edits cause torn writes, lost updates, and corrupted frontmatter. Off-the-shelf database solutions were rejected to keep the wiki purely file-based (git-friendly, no runtime daemon). The system needed three guarantees: mutual exclusion for page writes, crash-safe file updates, and detection of concurrent modification.
- **Decision:** A three-tier concurrency system was implemented. Tier 1 — `WikiLock` (`lock_wiki.py`): per-page advisory file locks via portalocker, with staleness detection (timeout-based primary, Unix PID fast-path secondary). Each lock file records PID, timestamp, and hostname. Tier 2 — `atomic_write.py`: writes to a `.tmp.<PID>` file in the same directory, fsyncs, then `os.rename()` to the target path (atomic on POSIX). Tier 3 — `content_hash.py`: SHA256 of page content stored in a `_content_hash` frontmatter field. On write, the expected hash is compared against the current hash — a mismatch means a concurrent edit happened and the write is rejected.
- **Consequences:** Easier: three independent tiers can be used separately or together depending on the operation's criticality. No database, no daemon — stays git-friendly. Harder: the lock + hash + atomic write is not a distributed transaction — it prevents corruption but doesn't provide total ordering. Crash recovery of `.tmp` files requires eventual cleanup.
